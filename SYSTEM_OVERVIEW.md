## 1. Project Identity

**Name:** RHUConnect
**Purpose:** Multi-role clinic management system for a Rural Health Unit (RHU) — Sierra Bullones, Bohol. Capstone-quality build.
**Target user today:** RHU staff only. There is still no patient-facing portal — unauthenticated visitors see only the login page. (A design for a future patient-facing booking portal exists — see §6 — but no code has been written for it.)

### Roles

| Role name       | Can manage via User Mgmt | Notes                                              |
|-----------------|---------------------------|-----------------------------------------------------|
| `Administrator` | No (seeded only)          | Cannot be created through the UI                    |
| `Doctor`        | Yes                       | Self-scoped everywhere: own appointments, own Visit History, own Vitals visibility |
| `Nurse`         | Yes                       | Owns Smart Queue call-next and Vitals/Triage recording |
| `Midwife`       | Yes                       | Self-scoped to own assigned prenatal cases (mirrors Doctor's self-scoping, not Nurse's clinic-wide pattern) |
| `Data Encoder`  | Yes                       | Read-only on Visit History and the SMS Notifications log |

### 4.14 SMS Notifications — updated: real gateway wired, not yet live

`SmsNotificationService` now has two modes, selected automatically by whether `SEMAPHORE_API_KEY` is set:
- **Unset (current production state):** identical simulated behavior as before — logs a `Sent` row immediately, no network call, zero cost.
- **Set:** calls `POST https://api.semaphore.co/api/v4/messages` via Laravel's HTTP client. A successful response marks `Sent`; an error response or a thrown exception (timeout, connection refused) marks `Failed` — critically, **a dead gateway never blocks the appointment action itself** (booking/approving/cancelling always succeeds; only that one SMS's own `delivery_status` reflects the gateway problem). Covered by 3 dedicated tests (`SmsNotificationTest`) using `Http::fake()` for success, API-error, and thrown-exception paths.

**Not yet live**, because:
- Semaphore was evaluated first — rejected as too expensive for this project's budget (minimum top-up ₱2,800 for 5,000 credits + 12% VAT).
- Two cheaper alternatives were researched: **PhilSMS** and **UniSMS** (both ~₱0.35/SMS, no forced minimum top-up). UniSMS additionally grants free trial credits on signup with no purchase required, and has an explicit "students using our API for a school project" support channel.
- An account was created on Semaphore for testing (0 credits, not yet funded) and on UniSMS (6 free trial credits granted, untested). **The trial UniSMS Sender ID only delivers to Globe/DITO networks, not Smart/TNT** — a real limitation to know about before assuming a test message "failed" when it's actually a network restriction on the shared trial sender ID.
- 16 simulated test-log entries from earlier manual testing were cleared (soft-deleted, recoverable via `withTrashed()`) so the SMS Notifications log starts clean once a real provider is wired up.

Whichever gateway is funded, wiring it in is a small, contained change — swap the `dispatch()` method's endpoint/field names in `SmsNotificationService`, nothing else in the codebase needs to change.

### 4.16 Maternal Care (Midwife) — new, fully built

**Real gap closed.** The original Midwife dashboard was 100% `notYetActiveStat()` placeholders because there was no schema anywhere distinguishing a maternal-care visit from a general one. Now:

**Key files:** `app/Http/Controllers/PrenatalCaseController.php`, `app/Models/PrenatalCase.php`, `resources/views/prenatal-cases/*`.

**Design decisions (deliberate, confirmed in conversation):**
- A prenatal case is its own model (`prenatal_cases`: LMP, EDD, gravida, para, `is_high_risk` + free-text risk notes, lifecycle `status` enum, soft deletes) — spans an entire pregnancy, not squeezed into one appointment.
- `trimester` is a **computed accessor**, never a stored column — derived from `last_menstrual_period` against the current date every time it's read, so it can never silently go stale.
- **Actual check-in visits still flow through the existing Appointments/Queue/Vitals/VisitHistory pipeline unchanged** — a prenatal visit is booked, queued, vitals-recorded, and completed exactly like any other appointment. The only new thing is an optional `appointments.prenatal_case_id` tag linking it back to the ongoing case.
- **`appointments.doctor_id` still requires a real Doctor** — a Midwife cannot independently complete a prenatal appointment herself; that was an explicit, deliberate decision (not a limitation discovered later) to avoid touching `AppointmentController`'s core, already-tested Doctor-only completion validation.
- **Midwife dashboard/case access is self-scoped**, exactly like Doctor — each Midwife sees only her own assigned cases and appointments, not a clinic-wide pool. This was confirmed twice in conversation: once when the module was designed, and again after a real user actually asked "why do two Midwife accounts see different numbers" — the answer both times was that this is intentional, matching how two different Doctors also see different appointment loads.
- **Visit History access for Midwife is scoped to flagged maternal-care visits only** (`prenatal_case_id` set AND owned by that Midwife) — not clinic-wide access to unrelated patients' clinical notes, which was explicitly rejected earlier as an unnecessary privacy expansion.

### 4.13 Reports & Analytics — updated: premium chart-based redesign

**Rebuilt from a table-only page into a statistics dashboard.** Added:
- A KPI summary strip (Total Appointments, No-Show Rate, Avg Doctor Utilization, Avg Queue Turnaround) at the top — an at-a-glance read before the detail sections.
- **ApexCharts visualizations** for all 4 reports: a stacked bar for Appointment Volume (color-coded to the same status-tone palette used everywhere else in the app — amber/green/blue/gray/red for Pending/Approved/Completed/Cancelled/No Show), a horizontal bar for Doctor Utilization, a donut + bar for Patient Demographics (sex, age bracket), and a bar for Queue Turnaround by priority lane.
- Every existing table, empty state, and CSV export link is preserved beneath its chart — additive, not a replacement of the exact-value lookup path.

**Two real bugs fixed while rebuilding this page** (see §8): `median_minutes` had no rounding at all, and `min_minutes`/`max_minutes` were incorrectly assumed to always be clean integers (`diffInMinutes()` doesn't guarantee that) — both produced long unrounded decimals that visually overlapped adjacent cells.

## 6. Future Design: Patient Self-Service Portal (conceptual — not built)

Captured here because it was designed in real detail during a planning conversation and represents the actual next major body of work, once decided on.

**Confirmed decisions:**
- **Patients will have real accounts** (not a no-account/OTP-per-booking flow) — they log in to book, rather than only staff booking on their behalf or walking in.
- **Booking online does not create a Queue entry.** This requires no new logic — Queue entries are already created only by an explicit check-in action, entirely separate from booking, in the current codebase. A patient booking from home sits as `Pending`/`Approved` with zero queue presence until check-in happens, exactly like a staff-booked appointment does today.
- **Registering an account should create a real `patients` row immediately**, not a deferred stub — because a real account carries enough verified identity to justify it.

**Real architectural decision flagged, not yet resolved:** patient authentication must be a **separate auth guard** from the existing staff `users`/roles system, not folded into it — mixing patient login into the table every RBAC check (`hasRole()`, `role:Administrator` middleware) is built around risks a patient session accidentally being reachable by staff-only authorization logic. This wasn't just recommended in passing — it's the load-bearing decision the rest of the portal design depends on.

**Open questions surfaced, not yet decided:**
- Which fields are mandatory at self-registration vs. deferred to an in-person Nurse intake. Leaning: identity/contact fields (name, DOB, sex, contact, address) mandatory upfront; clinical fields (allergies, conditions, medications, blood type) deferred, since a first-time patient self-reporting these unsupervised is a real accuracy risk — but this hasn't been formally decided.
- Who performs check-in once a self-booked patient physically arrives: front-desk staff (zero new code, matches today) vs. a patient-triggered "I've arrived" button (convenient, but doesn't actually verify physical presence — it just relocates the same button, doesn't add real location verification).
- Rate limiting / bot protection for a genuinely public-facing surface — this app has never had to defend against unauthenticated traffic before; every other route is staff-session-gated.
- Whether unapproved public Pending bookings should auto-expire, since Pending appointments already count as "booked" against a doctor's slot availability — a flood of unreviewed public requests could passively fill a calendar with nothing actually confirmed.

**Scope assessment:** this is closer to "build a second, patient-facing application that shares a database" than a feature addition to the existing staff app — a new auth guard, an entirely separate public-facing UI (not `layouts.dashboard`), and a new registration→patient-record pipeline. Recommended to plan as its own staged effort (auth guard → registration-creates-record → self-service booking reusing existing slot logic → optional self-check-in) rather than one master prompt, given the size.

## 8. Known Fixed Bugs / Patterns to Preserve (new entries since last regeneration)

| Pattern                                                                 | Status | Evidence |
|---------------------------------------------------------------------------|--------|------------|
| **`ReportsService::median()` had no rounding** | ✅ Fixed | Unlike `avg_minutes` (`round($minutes->avg(), 1)`), `median()` returned raw unrounded floats (e.g. `12.766666666666667`), visually overflowing into the adjacent grid cell. Now rounds to 1 decimal, matching the rest of the page. |
| **`min_minutes`/`max_minutes` incorrectly assumed integer-only** | ✅ Fixed | `diffInMinutes()` doesn't guarantee a clean integer; a real example (`2.0166666666667`) surfaced this. Same fix applied — both now rounded. |
| **Admin dashboard "Generate Reports" Quick Action — stale placeholder** | ✅ Fixed | `'route' => null` was left over from before Reports & Analytics existed — the exact same class of bug as the earlier "Patients Waiting" Doctor-dashboard placeholder. One test (`AdminAccessTest`) had to be updated in place since it was correctly asserting the old (correct-at-the-time) muted behavior. |
| **Appointments show page — empty "Update Status" card for non-managing viewers** | ✅ Fixed | A Doctor viewing another doctor's appointment saw a titled card with zero buttons inside it (both `$canManage` and `$canComplete` false for that viewer). Now the whole card is conditional on `$canManage \|\| $canComplete`. |
| **Smart Queue skeleton flicker on every 10s poll** | ✅ Fixed | `refreshing` was used to gate the loading skeleton on every background poll, not just first load — for a genuinely empty queue this flashed the skeleton in and out every ~10 seconds even though nothing changed. Removed the skeleton-during-poll behavior entirely, since Queue's data is seeded synchronously at page load and a loading state for a background refresh was never actually needed. |
| All patterns from the first regeneration (CSV injection fix, nav unification, Profile layout fix, legacy table removal, booked-slot subtraction, etc.) | ✅ Still holding | Re-verified during this pass; no regressions found. |
