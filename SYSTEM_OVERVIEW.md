# RHUConnect — System Overview

> **Internal engineering reference.** Generated by direct inspection of routes, controllers, models,
> migrations, middleware, tests, Blade views, and Alpine.js components. All claims are evidence-based.
> Ambiguities are called out explicitly rather than assumed.
>
> This is a full regeneration of the original overview — every module that document listed as
> "not yet implemented" has since been built. Treat this version as authoritative; the previous
> one described a materially earlier state of the codebase.

---

## 1. Project Identity

**Name:** RHUConnect
**Purpose:** Multi-role clinic management system for a Rural Health Unit (RHU). Intended as a production-quality capstone project for Sierra Bullones, Bohol.
**Target user:** RHU staff (not public patients — there is no patient-facing portal). Unauthenticated users see only the login page.

### Roles

Roles are stored as rows in the `roles` table (no enum). The five role names in active use, confirmed from `UserManagementController::MANAGED_ROLES` and role-gating constants across controllers:

| Role name       | Can manage via User Mgmt | Notes                                              |
|-----------------|--------------------------|-----------------------------------------------------|
| `Administrator` | No (seeded only)         | Created via seeder/`.env` vars; cannot be created through the UI |
| `Doctor`        | Yes                      | Owns availability self-management; only role (besides Administrator) that can mark an appointment Completed/No Show |
| `Nurse`         | Yes                      | Can archive patient records; owns Smart Queue and Vitals/Triage |
| `Midwife`       | Yes                      | Deliberately excluded from Visit History and Vitals read access — see §4.5 and §4.9 |
| `Data Encoder`  | Yes                      | Read-only on Visit History and SMS Notifications log |

Administrator cannot create another Administrator through the User Management UI — `MANAGED_ROLES` explicitly excludes it.

## 4. Completed / Production-Ready Modules

Everything in this section has real controllers, views, RBAC enforcement, and feature test coverage.

### 4.1 Authentication & Login, 4.2 Role-Specific Dashboards, 4.3 Patient Records, 4.5 RBAC Security, 4.6 User Management, 4.7 Global Search, 4.8 Notification Bell, 4.9 Profile Management

Unchanged in substance from the original overview, with two corrections:

- **Dashboards no longer have hardcoded stats.** Every stat card, primary table, and secondary list across all 5 dashboards is now backed by `DashboardStatsService` — real queries against `appointments`, `queues`, `patients`, `vitals`. Where a referenced module genuinely doesn't exist yet (Reports/Analytics numbers on non-admin dashboards, SMS-related counts before Data Encoder's stat was wired, maternal-care tracking for Midwife), the service returns an honest `notYetActiveStat()` gray placeholder rather than a fabricated number — this pattern is intentional and should be preserved for any future stat that also lacks real backing data.
- **Profile now renders through `layouts.dashboard`**, matching every other authenticated page. It used to render via the Breeze-default `<x-app-layout>` (a different, plainer shell) — that was a genuine bug, not a design choice; see §8.

**Notification bell test coverage**: previously zero dedicated coverage (only incidental assertions from other tests). `tests/Feature/NotificationTest.php` now covers index scoping, mark-as-read, mark-all-as-read, and — importantly — that a user cannot mark another user's notification as read by guessing its ID (`markAsRead` correctly 404s; verified as a real IDOR check, not just a happy-path test).

### 4.4 Doctor Availability

Unchanged in design (templates + exceptions, on-the-fly slot generation), but `DoctorAvailabilityService::getAvailableSlots()` **now subtracts already-booked appointment slots** — the original overview's flagged risk ("does NOT yet exclude already-booked appointment slots") is resolved. The service accepts an optional `$excludeAppointmentId` so editing an existing appointment doesn't hide its own currently-held slot. Booked slots are excluded for Pending/Approved/Completed appointments; Cancelled/No Show free the slot back up.

### 4.10 Online Appointments

**Fully built** — this was the single biggest gap in the original overview and is now the backbone several other modules hang off of.

**Key files:** `app/Http/Controllers/AppointmentController.php`, `resources/views/appointments/*`, `tests/Feature/AppointmentsTest.php` (10 tests).

**Design decisions (evidence-based, not assumed):**
- Slot generation is on-the-fly via `DoctorAvailabilityService`, not pre-generated (`appointment_slots` was deliberately dropped rather than built out — see §8).
- Booking roles: Administrator, Nurse, Midwife, Data Encoder (`AppointmentController::BOOKING_ROLES`). Doctor cannot book but can view.
- Status lifecycle: Pending → Approved/Cancelled → Completed/No Show, enforced via `AppointmentController::updateStatus()`.
- **Only the assigned Doctor or an Administrator can mark Completed/No Show** — enforced in `canTransitionToCompletion()`. All other status transitions are open to any booking role.
- **Marking Completed requires a diagnosis** and atomically creates the linked `VisitHistory` record in the same DB transaction — an appointment cannot be Completed without a clinical record existing for it, and a second completion attempt on an already-completed appointment fails cleanly (checked via `$appointment->visitHistory()->exists()`).
- Conflict checking: `appointmentAttributes()` validates the requested time against `DoctorAvailabilityService::getAvailableSlots()` for that doctor/date — booking or editing into an unavailable slot is rejected server-side, not just hidden in the UI.
- `patients.contact_number` now has a real `UNIQUE` DB constraint (previously flagged as a risk) — `PatientController` surfaces "A patient with this contact number already exists" as a clean validation error on collision.

### 4.11 Smart Queue

**Fully built.** Two-column live board (Waiting / Serving), priority-lane ordering, and a status lifecycle synced from the appointment record.

**Key files:** `app/Http/Controllers/QueueController.php`, `app/Services/QueueService.php`, `resources/views/queue/*`, `tests/Feature/QueueTest.php` (10 tests).

**Design decisions:**
- A queue entry requires an existing appointment (`queues.appointment_id` is a `UNIQUE` FK) — there is no walk-in-without-appointment path in this schema. Check-in happens via a "Check In" button on the appointment show page for a Pending/Approved appointment scheduled today.
- **Queue numbering is lane-separated**, matching Philippine RHU convention: Regular patients get `R-001, R-002, ...`; Senior Citizen/PWD/Pregnant share a `P-001, P-002, ...` sequence, both reset daily (`QueueService::nextQueueNumber()`).
- **`callNext()` serves priority lanes ahead of Regular**, oldest check-in first within each lane (`ORDER BY CASE WHEN priority_type = 'Regular' THEN 1 ELSE 0 END, id`).
- **`Serving → Completed` is automatic**, not a manual Nurse action — `QueueService::syncFromAppointmentStatus()` is called from within `AppointmentController::updateStatus()`'s transaction, so the queue entry closes out the instant the assigned Doctor marks the appointment Completed/No Show/Cancelled. Nurse/Administrator still manually drive `Waiting → Serving` (call next) and manual `Skipped`/`Cancelled` overrides.
- Check-in roles: Administrator, Nurse, Midwife, Data Encoder. Manage roles (call-next, manual status): Administrator, Nurse only.

### 4.12 Patient Visit History

**Fully built.** Created automatically as a side effect of completing an appointment (see §4.10) — there is no standalone "create visit history" form.

**Key files:** `app/Http/Controllers/VisitHistoryController.php`, `resources/views/visit-history/*`, `tests/Feature/VisitHistoryTest.php` (7 tests).

**RBAC (deliberately asymmetric, confirmed intentional):**
- Administrator: full read access, all records.
- Doctor: read-only, **own patients' records only** — `VisitHistoryController::show()` explicitly blocks a Doctor from viewing another doctor's visit history by ID (a real IDOR check, not an oversight).
- Nurse, Data Encoder: read-only, clinic-wide.
- **Midwife: no access at all.** This was a deliberate decision, not a gap — `visit_histories` holds real clinical content (diagnosis, prescription, notes), and there's no maternal-specific flag in the schema to scope a filtered view. Granting clinic-wide read access to full clinical notes for a role with no clinical relationship to most of those visits was judged an unnecessary privacy expansion. Midwife's "Visit History" nav label remains intentionally unwired (`app/Support/Navigation.php`) — revisit only if the schema gains a real maternal-care distinction.

### 4.13 Reports & Analytics

**Fully built** — Administrator-only, 4 metrics, CSV export, flexible date ranges.

**Key files:** `app/Http/Controllers/Admin/ReportsController.php`, `app/Services/ReportsService.php`, `resources/views/admin/reports/index.blade.php`, `tests/Feature/ReportsTest.php` (8 tests).

**Metrics:** Appointment volume + no-show rate (day-by-day), Doctor utilization (booked vs. capacity, using `DoctorAvailabilityService` as the same source of truth the booking flow uses), Patient demographics (sex/age-bracket/barangay breakdown, top 10 barangays + "Other"), Queue turnaround (check-in-to-completion duration, overall and per priority lane).

**Time ranges:** Today / This Week / This Month presets, plus a custom `from`/`to` date-range picker — chosen specifically because RHU compliance reporting periods rarely align to calendar boundaries.

**Delivery:** on-screen + CSV export per metric (no PDF — deliberately deferred; the browser's own print-to-PDF covers ad hoc printing needs without adding a PDF-generation dependency).

**Mobile:** the two table-shaped reports (Appointment Volume, Doctor Utilization) render as stacked cards below the `sm` breakpoint instead of a horizontally-scrolled wide table — a genuine UX fix applied after the initial build, not present from day one (see §8).

**Security note:** CSV export previously had a formula-injection vulnerability (CWE-1236) — see §8 and §10.

### 4.14 SMS Notifications

**Built, but deliberately simulated — no real gateway.** This is a product decision, confirmed with the project owner, not an incomplete implementation.

**Key files:** `app/Http/Controllers/SmsNotificationController.php`, `app/Services/SmsNotificationService.php`, `resources/views/sms-notifications/index.blade.php`, `tests/Feature/SmsNotificationTest.php` (6 tests).

**Behavior:** `SmsNotificationService` logs a row to `sms_notifications` with `delivery_status = 'Sent'` and `sent_at = now()` at two trigger points — appointment booking (confirmation message) and appointment status change to Approved or Cancelled (approval/cancellation notice). No outbound network call is made anywhere. Marking an appointment Completed does **not** log an SMS (confirmed by test).

**RBAC:** Administrator (full log) and Data Encoder (read-only) only — no other role has access; this isn't clinical data.

**To wire a real gateway later:** replace the body of `SmsNotificationService::send()` with an actual provider API call and let `delivery_status` reflect the real response — the two call sites in `AppointmentController` don't need to change.

### 4.15 Vitals/Triage

**Fully built.**

**Key files:** `app/Http/Controllers/VitalsController.php`, `app/Models/Vitals.php`, `resources/views/vitals/index.blade.php` (+ inline recording UI on `appointments/show.blade.php`), `tests/Feature/VitalsTest.php` (6 tests).

**Design decisions:**
- Fields: blood pressure (systolic/diastolic), temperature (°C), pulse rate, respiratory rate, oxygen saturation (%), weight (kg), height (cm), chief complaint (free text, nullable). Validation bounds are clinically sane (e.g. BP 40–300/20–200, temp 30–45 °C) — reject-garbage-input guardrails, not real medical validation.
- **Tied directly to the Appointment**, not the Queue check-in step — one vitals record per appointment (`vitals.appointment_id` is a `UNIQUE` FK).
- Recording: Nurse or Administrator only, for a Pending/Approved appointment scheduled today, and only once per appointment (a clean validation error on a second attempt, not a raw DB exception).
- **Two separate surfaces by design**: `VitalsController::index()` is a Nurse/Administrator-only daily overview list (mirrors the operational-dashboard role Smart Queue's board plays — a Nurse triaging many patients needs a running list, not per-appointment lookups). The full per-patient detail (all 8 values + chief complaint + who recorded it) lives inline on the appointment show page, visible to Administrator, Nurse, and the *assigned Doctor only* for their own patients — Midwife and Data Encoder get no access, consistent with the Visit History precedent.

## 7. Navigation Architecture (new section)

Sidebar navigation used to be defined independently in three places (`DashboardController::navigationFor()`, `GlobalSearchController::NAV_BY_ROLE`, and 16 individual view files each with their own copy-pasted `$navGroups` PHP block) — a manual-sync duplication risk the old `GlobalSearchController` even had a comment warning about.

**Now:** `app/Support/Navigation.php::forRole(string $roleName): array` is the single canonical definition (nested groups, each item either a bare string placeholder or `['label', 'route', 'active']`). `AppServiceProvider::boot()` registers a `View::composer('layouts.dashboard', ...)` that injects `navGroups`/`roleLabel`/`portalLabel` automatically for every view extending that layout — no controller or view computes navigation locally anymore. `GlobalSearchController`'s command-palette search derives its results from `Navigation::flatLabelsForRole()`/`routesForRole()` rather than maintaining its own separate list.

**Verified consequence of this refactor:** a real, previously-shipped bug (Nurse's Cmd+K search was missing an "Appointments" result that existed in the sidebar) was fixed automatically as a side effect of unifying the source of truth, not through a separate patch.
